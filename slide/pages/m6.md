# 3. The simple solution: `page.route`

```ts {1-3|4-12|14-18|all}
test('payment gateway declines: user sees a clear message', async ({ page, onBookingForm, paymentPage }) => {
  await page.route('**/api/payments/charge', (route) =>
    route.fulfill({ status: 500, json: { error: 'gateway_unavailable' } }));   // no real charge

  await onBookingForm.fill(passenger());
  await onBookingForm.continueToPayment();
  await paymentPage.pay(CARD);

  await expect(page.getByText("We couldn't process your payment. Please try again."))
    .toBeVisible();
});

test('mocked search: backend down shows the error state', async ({ page }) => {
  await page.route('**/api/flights/search*', (r) => r.fulfill({ status: 500, json: {} }));
  await page.goto('/flights/results?origin=BKK&destination=SIN&departure=2026-12-01&passengers=1&cabin=economy');
  await expect(page.getByText('Something went wrong loading flights.')).toBeVisible();
});
```

<!--
SAY: Register the route BEFORE the action that triggers the request. `route.fulfill` answers instead of the server: status, JSON, headers. The decline test never reaches a real charge, finishes fast, and proves the user sees a clear message instead of a spinner.
Also: `route.fulfill({ json: { flights: [] } })` gives you the empty state for free, a case that is awkward to produce with real data.
Q: "Does the order of routes matter?" Later-registered routes win. In this repo the fixture registers a bridge first; your test route is registered later and takes precedence.
TIME: 5 min.
NEXT: And the API itself can be tested without a browser.
-->

# API assertions and test data via API

```ts {1-9|11-17|all}
test('API contract: search returns well-formed flights', async ({ request }) => {
  const res = await request.get(`${QOOMLEE_API}/api/flights/search`, {
    params: { origin: 'BKK', destination: 'SIN', date: day },
  });
  expect(res.ok()).toBeTruthy();
  const { flights } = await res.json();
  expect(flights[0]).toMatchObject({ origin: 'BKK', currency: 'THB',
    flightNumber: expect.stringMatching(/^[A-Z]{2}\d{3}$/) });
});

test('data via API: a booking created with zero clicks shows up in the UI', async ({ page, request }) => {
  await page.goto('/flights');
  const token = await page.evaluate(() => localStorage.getItem('qoomlee:session:token'));
  const ref = await createBookingViaApi(request, token!, flight);
  await page.goto('/bookings');
  await expect(page.getByText(ref)).toBeVisible();
});
```

<!--
SAY: `request` is an HTTP client, no browser needed: fast checks of the contract. And it is the fastest way to build test data: instead of clicking through search, select and passenger forms, call the booking endpoint and open the UI right where the interesting part begins.
Rule of thumb: arrange through the API, act and assert through the UI.
Q: "Is calling the API from a test cheating?" For arrange, no: the thing under test is the screen, not how the data got there. Keep the UI path covered by one journey.
TIME: 4 min.
NEXT: Run all of it.
-->

::criteria::
- [ ] Decline test never reaches a real charge
- [ ] No test clicks to create data an API call can
- [ ] Routes registered **before** the trigger

::hint::
`route.fulfill({ status: 500, json: { ... } })`. Register the route before the click.

::recap::
- `page.route` + `fulfill`: **control** the backend to test errors and empty states
- `request`: API checks and **fast test data**, no browser needed
- Keep **one** real journey; mock the rest
